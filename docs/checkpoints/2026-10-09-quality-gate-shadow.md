## تصمیم‌های معماری

1. در این PR، Quality Gate فقط Shadow است و دادهٔ خام یا فهرست عمومی را تغییر نمی‌دهد.
2. precision بر recall مقدم است؛ پسوند «اردکانی» فقط سیگنال ضعیف است.
3. خطای دسترسی به منبع، شاهد عدم وجود فرد نیست.
4. تبدیل همهٔ گزاره‌ها به claim منبع‌دار، migration جداگانه می‌خواهد و در این PR نیمه‌کاره پیاده نشده است.
5. Backend محلی داشبورد `http.server` است؛ عملیات ماندگار مدیریتی از Cloudflare Worker/D1 استفاده می‌کند، نه FastAPI.

## محدودیت‌ها و ریسک‌ها

- قواعد شخص‌بودن و locality هنوز heuristic هستند و بدون مجموعهٔ طلایی، precision/recall/F1 قابل دفاع نیست.
- فقط یک تصمیم تأیید انسانی معتبر در Snapshot وجود دارد.
- برخی رکوردها URL یا قطعه‌شاهد کافی ندارند و عمداً عبور نمی‌کنند.
- Quality Gate برای تشخیص duplicate از خروجی Entity Resolution استفاده می‌کند؛ بازطراحی کامل ترتیب pipeline باید در PR بعدی انجام شود.
- Entity Resolution روی Snapshot کامل blocking/index مؤثر ندارد و تست واقعی آن برای CI بیش از حد کند است.
